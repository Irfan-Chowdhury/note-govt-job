# 📘 3. Handnote: Server Scaling ও Storage Technologies

## প্রশ্ন ১২: Horizontal Scaling বনাম Vertical Scaling

### Scaling কী?
চাহিদা (ব্যবহারকারী/Data) বাড়লে Server-এর ক্ষমতা বাড়ানোকেই **Scaling** বলে। এটি দুইভাবে করা যায়।

> **সহজ উপমা:** একটি রেস্টুরেন্টে ভিড় বাড়ল।
> - **Vertical:** একজন রাঁধুনিকেই আরও বড় চুলা ও দ্রুত যন্ত্র দেওয়া।
> - **Horizontal:** আরও রাঁধুনি নিয়োগ দেওয়া এবং কাজ ভাগ করে দেওয়া।

### Vertical Scaling (Scale Up)
**একটি Server-এর ভেতরেই** CPU, RAM, Disk **বাড়ানো বা আরও শক্তিশালী Server-এ বদলানো**।

### Horizontal Scaling (Scale Out)
**আরও Server যোগ করে** কাজ ভাগ করে দেওয়া। এর জন্য **Load Balancer** লাগে, যা Request সব Server-এ ভাগ করে।

### চিত্র (Server Rack সহ)

```
VERTICAL (Scale Up)                  HORIZONTAL (Scale Out)
একই Server-কে শক্তিশালী করা            Server-এর সংখ্যা বাড়ানো

  আগে          পরে                     Users
 ┌──────┐    ┌──────────┐                │
 │Server│    │ Server   │          ┌─────▼──────┐
 │ 8 GB │ →  │ 128 GB   │          │Load Balancer│
 │ 2 CPU│    │ 32 CPU   │          └─┬────┬────┬─┘
 └──────┘    └──────────┘            │    │    │
 (একই মেশিন, বেশি ক্ষমতা)         ┌───▼┐ ┌─▼──┐ ┌▼───┐
                                   │Srv1│ │Srv2│ │Srv3│ ...নতুন যোগ
                                   └────┘ └────┘ └────┘
```

### তুলনা

| বিষয় | **Vertical (Scale Up)** | **Horizontal (Scale Out)** |
|---|---|---|
| **পদ্ধতি** | একই Server-এ CPU/RAM/Disk বাড়ানো | আরও Server যোগ করা |
| **Downtime** | সাধারণত **লাগে** (Upgrade-এর সময় বন্ধ) | সাধারণত **লাগে না** |
| **সীমা** | **আছে** (Hardware-এর সর্বোচ্চ সীমা) | **প্রায় সীমাহীন** |
| **Single Point of Failure** | **আছে** (Server নষ্ট = সব বন্ধ) | **নেই** (একটি নষ্ট হলে বাকিরা চলে) |
| **খরচ** | শুরুতে সহজ, কিন্তু উচ্চ-ক্ষমতার Server খুব **দামি** | Commodity Server সস্তা, তবে সংখ্যা বাড়ায় মোট খরচ বাড়ে |
| **জটিলতা** | **সহজ** (Application বদলাতে হয় না) | **জটিল** (Load Balancer, Data Sync লাগে) |
| **Load Balancer** | লাগে না | **লাগে** |
| **Fault Tolerance** | কম | **বেশি** |
| **উপযোগী** | **Database**, ছোট ও পুরনো Application | **Web Server**, বড় Cloud Application |

### Real Scenario
ঈদের আগে একটি e-commerce সাইটে হঠাৎ ভিড় বাড়ল।
- **Vertical:** Server-এর RAM ৮ থেকে ৬৪ GB করা। সহজ, কিন্তু Upgrade-এ সাইট কিছুক্ষণ বন্ধ থাকতে পারে, আর একসময় Hardware-এর সীমা এসে যায়।
- **Horizontal:** ২টির জায়গায় ১০টি Web Server চালু করে Load Balancer দিয়ে Traffic ভাগ। একটি নষ্ট হলেও সাইট চলে।

### Laravel Reference
Laravel App **Horizontal Scale** করতে হলে Server যেন "Stateless" থাকে, তাই Session, Cache ও Queue একটি **শেয়ারড জায়গায়** রাখতে হয়:

```env
SESSION_DRIVER=redis     # Session সব Server-এ শেয়ার
CACHE_DRIVER=redis       # Cache শেয়ার
QUEUE_CONNECTION=redis   # Queue শেয়ার
FILESYSTEM_DISK=s3       # Upload করা ফাইল শেয়ারড Storage-এ
```
Database সাধারণত আগে **Vertical** বাড়ানো হয়, পরে **Read Replica** যোগ করে Horizontal করা হয়।

## প্রশ্ন ১৩: SAS বনাম SATA

### পরিচয়
| | পূর্ণ নাম | মূল ব্যবহার |
|---|---|---|
| **SATA** | **Serial ATA** | সাধারণ কম্পিউটার, Desktop, বড় Capacity সস্তায় |
| **SAS** | **Serial Attached SCSI** | Enterprise Server, Data Center |

> **উপমা:** SATA হলো সাধারণ **একমুখী রাস্তা**, যেখানে এক সময়ে এক দিকেই গাড়ি চলে। SAS হলো **দুই লেনের হাইওয়ে**, যেখানে একসাথে আসা-যাওয়া চলে।

### তুলনা

| বিষয় | **SATA** | **SAS** |
|---|---|---|
| **গতি (Interface)** | SATA III = **6 Gbps** (~600 MB/s) | SAS-3 = **12 Gbps**, SAS-4 = **22.5 Gbps** |
| **Disk-এর ঘূর্ণন (HDD)** | **5400/7200 RPM** | **10,000/15,000 RPM** |
| **Duplex** | **Half-duplex** (এক সময়ে এক দিকে) | **Full-duplex** (একসাথে Read ও Write) |
| **Port** | **Single Port** | **Dual Port** (একটি ব্যর্থ হলে অন্যটি চলে) |
| **Command Queue** | কম (**32**) | বেশি (**256**) |
| **Reliability** | কম (বেশিরভাগ Consumer-grade) | **বেশি**, Error Rate কম |
| **MTBF (আনুমানিক)** | ~১–১.২ মিলিয়ন ঘণ্টা | ~১.৬–২ মিলিয়ন ঘণ্টা |
| **সংযুক্ত Device** | কম | **হাজারেরও বেশি** (Expander দিয়ে) |
| **Cable দৈর্ঘ্য** | ~১ মিটার | ~১০ মিটার |
| **খরচ (প্রতি GB)** | **সস্তা** | **দামি** |
| **Capacity** | **বেশি** (বড় ডিস্ক সস্তায়) | তুলনামূলক কম |
| **Compatibility** | SAS Controller-এ **চলে** | SATA Controller-এ **চলে না** |

**কোনটি Server-এর জন্য সেরা?**

| প্রয়োজন | সেরা |
|---|---|
| **Database, ব্যাংকিং, Virtualization, মিশন-ক্রিটিক্যাল Server** | **SAS** (গতি, নির্ভরযোগ্যতা, Redundancy) |
| **Backup, Archive, File Storage, বাজেট কম** | **SATA** (সস্তায় বেশি Capacity) |

**উত্তর:** Server-এর জন্য, বিশেষ করে ২৪×৭ চলা Enterprise Server-এ, **SAS** শ্রেয়, কারণ এতে গতি বেশি, Dual Port ও Full-duplex থাকায় নির্ভরযোগ্যতা উন্নত। তবে খরচ সীমিত থাকলে ও কম লোডের কাজে (Backup/Archive) **SATA** উপযুক্ত। বাস্তবে প্রতিষ্ঠান **দুটোই মিশিয়ে (Tiered Storage)** ব্যবহার করে।

> **নতুন যুগ:** SSD-তে **NVMe** (PCIe-ভিত্তিক) SAS ও SATA-র চেয়েও দ্রুত।

## প্রশ্ন ১৪: RAID

### RAID কী?
**RAID = Redundant Array of Independent (পুরনো নাম: Inexpensive) Disks**।
একাধিক Hard Disk-কে একত্র করে একটি **Logical Disk**-এর মতো ব্যবহার করা, যাতে **গতি বাড়ে, Data নিরাপদ থাকে, বা দুটোই হয়**।

### RAID-এর তিনটি মূল কৌশল

| কৌশল | মানে | উপমা |
|---|---|---|
| **Striping** | Data টুকরো করে একাধিক Disk-এ ভাগ | বই-এর পাতা দুই বন্ধুকে ভাগ করে পড়া (দ্রুত) |
| **Mirroring** | Data-র **হুবহু কপি** আরেক Disk-এ | একই বইয়ের দুটি কপি রাখা (নিরাপদ) |
| **Parity** | হিসাব করা **যাচাই-তথ্য**, যা দিয়ে নষ্ট Data ফেরানো যায় | যোগফল মনে রাখা, একটি সংখ্যা হারালে যোগফল থেকে বের করা |

**Parity সহজ উদাহরণ:** A = 1, B = 0 হলে Parity = A XOR B = **1**। যদি B নষ্ট হয়, তবে **B = A XOR Parity = 1 XOR 1 = 0** ফিরে পাওয়া যায়।

### প্রতিটি RAID-এর চিত্র

```
RAID 0 (Striping)         RAID 1 (Mirroring)        RAID 5 (Distributed Parity)
Disk1   Disk2             Disk1   Disk2             Disk1  Disk2  Disk3
┌────┐  ┌────┐            ┌────┐  ┌────┐            ┌────┐ ┌────┐ ┌────┐
│ A1 │  │ A2 │            │ A1 │  │ A1 │            │ A1 │ │ A2 │ │ Ap │
│ A3 │  │ A4 │            │ A2 │  │ A2 │            │ B1 │ │ Bp │ │ B2 │
└────┘  └────┘            └────┘  └────┘            │ Cp │ │ C1 │ │ C2 │
Data ভাগ হয়               Disk2 = Disk1-এর কপি       └────┘ └────┘ └────┘
(কোনো নিরাপত্তা নেই)                                  (p = Parity, সব Disk-এ ছড়ানো)

RAID 6 (Double Parity)                  RAID 10 (1+0 = Mirror-এর Stripe)
Disk1  Disk2  Disk3  Disk4                    ┌─ Stripe (RAID 0) ─┐
┌────┐ ┌────┐ ┌────┐ ┌────┐              Mirror 1          Mirror 2
│ A1 │ │ A2 │ │ Ap │ │ Aq │             Disk1  Disk2      Disk3  Disk4
│ B1 │ │ Bp │ │ Bq │ │ B2 │             ┌────┐ ┌────┐     ┌────┐ ┌────┐
│ Cp │ │ Cq │ │ C1 │ │ C2 │             │ A1 │=│ A1 │     │ A2 │=│ A2 │
│ Dq │ │ D1 │ │ D2 │ │ Dp │             │ A3 │=│ A3 │     │ A4 │=│ A4 │
└────┘ └────┘ └────┘ └────┘             └────┘ └────┘     └────┘ └────┘
(p ও q = দুই ধরনের Parity)
```

### তুলনা: RAID 0, 1, 5, 6, 10

| বিষয় | **RAID 0** | **RAID 1** | **RAID 5** | **RAID 6** | **RAID 10** |
|---|---|---|---|---|---|
| **কৌশল** | Striping | Mirroring | Striping + **একক** Parity | Striping + **দ্বৈত** Parity | Mirroring + Striping |
| **ন্যূনতম Disk** | 2 | 2 | **3** | **4** | **4** |
| **Fault Tolerance** | **নেই** | ১টি Disk | **১টি** Disk | **২টি** Disk | প্রতি Mirror জোড়ায় ১টি |
| **ব্যবহারযোগ্য Capacity** | **১০০%** | **৫০%** | **(n−1)/n** | **(n−2)/n** | **৫০%** |
| **Read গতি** | অসাধারণ | ভালো | ভালো | ভালো | অসাধারণ |
| **Write গতি** | অসাধারণ | মাঝারি | **ধীর** (Parity হিসাব) | **সবচেয়ে ধীর** | ভালো |
| **খরচ** | সবচেয়ে কম | বেশি (অর্ধেক নষ্ট) | মাঝারি | মাঝারি-বেশি | **সবচেয়ে বেশি** |
| **ব্যবহার** | Video Editing, Cache, Temporary Data | OS Disk, ছোট গুরুত্বপূর্ণ Data | File Server, সাধারণ Server | বড় Disk-এর Archive, গুরুত্বপূর্ণ Data | **Database**, High-performance Server |

**উদাহরণ (৪টি, প্রতিটি ১ TB):**

| RAID | ব্যবহারযোগ্য Capacity |
|---|---|
| RAID 0 | **৪ TB** |
| RAID 1 (২টি Disk) | **১ TB** |
| RAID 5 | **৩ TB** |
| RAID 6 | **২ TB** |
| RAID 10 | **২ TB** |

### কোনটি কখন বাছবেন?

```
Data হারালে চলবে?
   ├── হ্যাঁ চলবে, শুধু গতি চাই ──────────────► RAID 0
   └── না, নিরাপত্তা চাই
        ├── ছোট/OS Disk ───────────────────────► RAID 1
        ├── Capacity ও নিরাপত্তার ভারসাম্য ─────► RAID 5
        ├── ২টি Disk নষ্ট হলেও টিকতে হবে ──────► RAID 6
        └── গতি + নিরাপত্তা (Database) ─────────► RAID 10
```

### Real Scenario
ব্যাংকের **Database Server**-এ প্রতি সেকেন্ডে অসংখ্য Write হয় এবং Data হারানো চলবে না, তাই **RAID 10** (গতি ও নিরাপত্তা দুটোই)। আর অফিসের **File Server**-এ Capacity ও খরচের ভারসাম্যের জন্য **RAID 5** বা বড় Disk হলে **RAID 6**।

### Laravel Reference
আপনার Laravel App-এর **MySQL Database** Production Server-এ সাধারণত **RAID 10 (SSD)**-এ রাখা হয়, যাতে অনেক Query ও Write দ্রুত চলে এবং একটি Disk নষ্ট হলেও Data নিরাপদ থাকে।

## প্রশ্ন ১৫: SAN বনাম NAS

### পরিচয়

| | পূর্ণ নাম | সংক্ষেপে |
|---|---|---|
| **SAN** | **Storage Area Network** | Server-এর কাছে **কাঁচা ডিস্কের মতো (Block-level)** Storage, আলাদা দ্রুত Network-এ |
| **NAS** | **Network Attached Storage** | Network-এ **ফাইল ও ফোল্ডার (File-level)** শেয়ার করার Storage |

> **উপমা:**
> - **NAS** = অফিসের **শেয়ারড ফোল্ডার/ফাইল-কেবিনেট**। সবাই নেটওয়ার্ক দিয়ে ফাইল খুলে নেয়।
> - **SAN** = Server-কে একটি **নতুন Hard Disk** দেওয়া, যদিও সেটি দূরে অন্য ঘরে আছে। Server সেটিকে নিজের Disk ভাবে ও নিজের মতো ফরম্যাট করে।

### চিত্র

```
NAS (File-level, সাধারণ LAN)                SAN (Block-level, আলাদা দ্রুত Network)

 PC1   PC2   Server                         Server1   Server2   Server3
  │     │      │                               │         │         │
  └─────┴──────┴─── LAN Switch                 └────── FC / iSCSI Switch ──────┘
                       │                                     │
                 ┌─────▼─────┐                        ┌──────▼───────┐
                 │   NAS     │                        │ SAN Storage  │
                 │ (নিজস্ব    │                        │ (Disk Array, │
                 │ File System│                        │  LUN-এ ভাগ)  │
                 │  ও IP)     │                        └──────────────┘
                 └───────────┘
 NFS / SMB প্রোটোকলে ফাইল শেয়ার             Fibre Channel / iSCSI প্রোটোকলে Block Access
```

### তুলনা

| বিষয় | **SAN** | **NAS** |
|---|---|---|
| **Access ধরন** | **Block-level** | **File-level** |
| **Network** | **আলাদা** উচ্চ-গতির (Fibre Channel/iSCSI) | **সাধারণ LAN** (Ethernet) |
| **Protocol** | **Fibre Channel, iSCSI, FCoE** | **NFS, SMB/CIFS**, FTP |
| **File System কে চালায়?** | **Server নিজে** (Storage-কে Local Disk ভাবে) | **NAS Device নিজে** |
| **Server কী দেখে?** | কাঁচা Disk (**LUN**) | শেয়ারড ফোল্ডার |
| **গতি/Latency** | **বেশি গতি, কম Latency** | মাঝারি (LAN-এর ওপর নির্ভর) |
| **Setup** | **জটিল** | **সহজ** |
| **খরচ** | **বেশি** | **কম** |
| **Scalability** | খুব ভালো (Enterprise স্তর) | সীমিত (মাঝারি) |
| **ব্যবহার** | **Database, Virtualization (VM), ERP, ব্যাংকিং** | **ফাইল শেয়ারিং, Backup, Home Directory, Media** |
| **Boot করা যায়?** | **হ্যাঁ** (SAN Boot) | না |

> **তৃতীয় ধরন DAS (Direct Attached Storage):** Storage সরাসরি একটি Server-এর সাথে যুক্ত (যেমন Server-এর ভেতরের Disk বা USB Disk), অন্য Server শেয়ার করতে পারে না।

### Real Scenario
- একটি অফিসে সবাই Word/Excel ফাইল শেয়ার করে, তাই **NAS**।
- ব্যাংকের Oracle Database ও VMware Virtual Machine-গুলো দ্রুত ও নির্ভরযোগ্য Storage চায়, তাই **SAN**।

### Laravel Reference
Laravel App **একাধিক Web Server-এ** (Horizontal Scaling) চালালে Upload করা ফাইল সব Server-এ পাওয়া দরকার। এজন্য **NAS (NFS) মাউন্ট** অথবা **S3 (Object Storage)** ব্যবহার হয়:
```php
Storage::disk('s3')->put('uploads/photo.jpg', $file);   // সব Server একই ফাইল পায়
```
এভাবে প্রশ্ন ১২ (Horizontal Scaling) ও ১৫ (NAS) একসূত্রে বাঁধা।

## 📌 মনে রাখার মতো তথ্য

**Scaling:**
- **Vertical = Scale Up** (একই Server শক্তিশালী); **Horizontal = Scale Out** (Server সংখ্যা বাড়ানো)।
- Horizontal-এ **Load Balancer** লাগে; Vertical-এ **Single Point of Failure** থাকে।
- **Database সাধারণত Vertical, Web Server সাধারণত Horizontal।**
- **Scale In/Out:** কমানো/বাড়ানো (Horizontal); **Scale Up/Down:** বাড়ানো/কমানো (Vertical)।

**SAS বনাম SATA:**
- **SAS = Serial Attached SCSI; SATA = Serial ATA।**
- **SATA III = 6 Gbps; SAS-3 = 12 Gbps।**
- **SAS: Full-duplex, Dual Port, 10K/15K RPM; SATA: Half-duplex, Single Port, 5400/7200 RPM।**
- **SAS Controller-এ SATA Disk চলে, উল্টোটা চলে না।**
- **SATA সস্তা ও বেশি Capacity; SAS দ্রুত ও নির্ভরযোগ্য।**

**RAID:**
- **RAID = Redundant Array of Independent Disks।**
- **RAID 0 = ১০০% Capacity কিন্তু Fault Tolerance নেই।**
- **ন্যূনতম Disk:** RAID 0/1 = ২, RAID 5 = ৩, RAID 6/10 = ৪।
- **Capacity:** RAID 5 = (n−1)/n, RAID 6 = (n−2)/n, RAID 1/10 = ৫০%।
- **RAID 5 = ১টি, RAID 6 = ২টি Disk নষ্ট সহ্য করে।**
- **RAID 10 = RAID 1 + RAID 0**, Database-এর জন্য সেরা।
- **RAID ≠ Backup!** RAID শুধু Disk নষ্ট থেকে বাঁচায়; ভুলে মুছে ফেলা, Virus বা আগুন থেকে নয়।
- **Hot Spare:** অপেক্ষায় থাকা বাড়তি Disk, একটি নষ্ট হলে নিজে থেকে Rebuild শুরু করে।
- RAID 5/6-এ **Parity** হিসাবের জন্য Write ধীর।

**SAN বনাম NAS:**
- **SAN = Block-level; NAS = File-level।**
- **SAN = Fibre Channel/iSCSI; NAS = NFS/SMB।**
- **SAN = আলাদা Network, দামি, দ্রুত; NAS = সাধারণ LAN, সস্তা, সহজ।**
- **File System:** SAN-এ **Server** চালায়, NAS-এ **Storage Device** চালায়।

## 🎯 পরীক্ষার টিপস
- **Scaling প্রশ্নে "diagram" চাইলে** দুটি চিত্র আঁকুন (Rack ও Load Balancer সহ) এবং পাশে তুলনার টেবিল লিখুন।
- **SAS vs SATA-তে** শেষে **"কোনটি Server-এর জন্য ভালো"** আলাদা অনুচ্ছেদে স্পষ্ট উত্তর দিন, কারণ প্রশ্নেই এটি চাওয়া হয়েছে।
- **RAID প্রশ্নে** শুরুতে Striping, Mirroring, Parity, এই তিন কৌশল লিখুন, তারপর টেবিল। **Capacity-র সূত্র** ও **উদাহরণ (৪ × ১ TB)** দিলে হিসাবের প্রশ্নেও কাজে লাগবে।
- **MCQ ফাঁদ:** RAID 0 "Redundant" নয় (কোনো Redundancy নেই), **RAID ≠ Backup**, **SAN = Block, NAS = File**, **SAS Controller-এ SATA চলে, SATA Controller-এ SAS চলে না।**
- **সম্পর্ক মনে রাখার কৌশল:** Horizontal Scaling → **শেয়ারড Storage** দরকার → **NAS/SAN** → Disk-কে নিরাপদ করতে **RAID**।
